## Temuan digiCamControl (penting untuk Mac & EDSDK nanti)

1. **Header `Content-Length` ganda** dari server Griffin-nya. `fetch` Node menolak (`UND_ERR_RES_CONTENT_LENGTH_MISMATCH`), `node:http` juga, termasuk `insecureHTTPParser` (`HPE_UNEXPECTED_CONTENT_LENGTH`). curl, PowerShell, dan .NET HttpClient (pemicu Camera Service) toleran. Booth memakai GET TCP mentah ke 127.0.0.1:5513.
2. **Dialog "Open Source"/donasi** (topmost, 460×380, judul `digiCamControl by Duka Istvan`) muncul ±11 s setelah start dan **menahan perintah jendela** (`CMD=Capture`, `LiveViewWnd_*`) sampai ditutup. `slc=get` tetap dijawab. Dari kode (ilspycmd, `MainWindow.xaml.cs`): dialog tidak dibuat kalau `Settings.StartMinimized` aktif atau `Branding.ShowWelcomeScreen=false`. `Branding.xml` dibaca dari **folder instalasi** (butuh admin). Booth mengubah `"StartMinimized": true` di `C:\ProgramData\digiCamControl\settings.json` sebelum membuka digiCamControl (hanya saat tidak berjalan, karena digiCamControl menulis ulang file itu saat keluar). Menutup dialog dengan WM_CLOSE lewat PowerShell tidak andal (ditinggalkan).
3. **ngrok**: digiCamControl menjalankan `ngrok.exe http 5513` saat start dan mencoba mengirim URL-nya ke digicamcontrol.com. Tanpa akun ngrok tidak ada tunnel (`/api/tunnels` kosong), jadi kamera tidak terbuka ke internet, dan log mencatat "Unable to start webserver" (menyesatkan, web server sendiri jalan). **ngrok yatim** dari instance yang dimatikan paksa membuat web server instance baru baru menjawab setelah 3–4 menit. Setelah ngrok dibersihkan, 5,5 s. Booth menjalankan `taskkill /IM ngrok.exe /F` sebelum membuka digiCamControl.
4. **Perintah jendela sebelum kamera selesai tersambung** (±10–12 s setelah start) membuat digiCamControl **macet permanen** (Show → Hide → Show dalam 4 s, lalu tidak ada perintah yang dijawab selama 90 s). Booth menunggu 20 s setelah web server hidup pada cold start.
5. Live view 700D butuh 1–2 s untuk frame pertama. Adapter membiarkan live view menyala di antara foto dalam satu sesi dan menyembunyikannya setelah 60 s idle.
6. Kotak hijau fokus tergambar di frame live view (setelan digiCamControl `ShowFocusRect`). Belum diubah.
7. Setiap 7 hari digiCamControl menjalankan cek update (`Branding.CheckForUpdate`), yang bisa memunculkan dialog versi baru. Belum terjadi, dicatat saja.

## Belum / usul untuk Mac

- **Setelan kamera di mode crew** (ISO, shutter, aperture, WB, pilih kamera): API `slc=list/get/set` sudah terbukti di 700D. Usul di issue #1 (Camera Service `camera.settings.*`, nanti EDSDK dengan kontrak sama).
- `--digicam` saat ini flag baris perintah. Sebaiknya masuk config device (pilih sumber kamera di mode crew).
- Opsional, butuh admin dan persetujuan Rama: `Branding.xml` di folder instalasi (tanpa dialog/splash/cek update) dan menonaktifkan `ngrok.exe`. Klasifikasi keamanan menolak rename/hapus di Program Files dari sesi otomatis.
- Jalur dengan Camera Service belum siap (sesi dimulai < 26 s setelah boot) → layar "kamera disiapkan ulang" lalu lanjut. Belum diuji panjang.

## Lanjutan: live view bersih & FPS (`win@6580c92`)

- `CMD=LiveView_NoProcess` (dari kode `LiveViewViewModel`): frame asli kamera diteruskan tanpa kotak fokus/overlay dan tanpa encode ulang. 960×640 tetap, ±270 KB/frame (sebelumnya ±35 KB).
- FPS terukur (5 s, frame unik): default 5,6/s, NoProcess 6,6/s. `/liveview.jpg` menjawab frame terakhir seketika, jadi batasnya di pembacaan live view digiCamControl (timer 50 ms + unduh EVF serial), bukan booth. 20–30 fps seperti dslrBooth butuh EDSDK langsung (Fase 1b).
- Bug diperbaiki: loop lama meminta frame tanpa jeda (±2000 permintaan/s, frame sama) sampai port lokal habis (16 ribu TIME_WAIT, `EADDRINUSE`). Sekarang main mengembalikan frame kosong kalau tidak berubah dan renderer menunggu 40 ms.
- 22:27:58 kamera terputus di tengah uji ("Camera disconnected", 700D hilang dari USB). Dugaan auto power off / baterai; sedang dicek Rama.
